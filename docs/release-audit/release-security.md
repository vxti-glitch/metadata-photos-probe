## Build and supply-chain observations

- Actions `checkout`, `cache`, and `upload-artifact` are pinned to commit SHA. CI grants `contents: read` and persists no checkout credentials. `pub get --enforce-lockfile` uses `editor/pubspec.lock`; Flutter bootstrap checks the exact framework commit and a clean tracked checkout. `Package.swift` has no external package dependencies.
- The `macos-15` runner image and selected Xcode installation are mutable; the script records the actual toolchain in evidence. It prefers Xcode 26.2 but allows 16.4 or the runner default. This is a recorded input, not a fully reproducible image. A missing `xcodeproj` Ruby gem is installed at an unpinned version, which can alter project-generation behavior across fresh runners. Pin that build dependency if repeatability is required.
- `scripts/editor-package.py` refuses an unexpected bundle/version/build, absent Photos usage description or scene configuration, embedded provisioning profile, identity-signed app in the unsigned path, stale camera catalog, and non-device/non-arm64 binaries. It writes explicit unsigned/untested fields in the manifest. Those checks qualify the package structure, not installation or media behavior.
- The editor workflow uploads the evidence directory and entire XCTest result bundle to a GitHub artifact. CI currently uses controlled fixtures; adding private media, filenames, GPS, or device identifiers to those tests would publish them through the public repository's artifacts. Review new tests and their logs before rerunning CI.
- `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` are enabled in the editor's Info.plist. This exposes app Documents through iOS file sharing/Files. Confirm the app stores only intended user-facing processed copies there; keep private staging and original working copies in Application Support or another private directory.
- `docs/BUILD-AND-INSTALL.md` and `docs/DEVICE-TEST-PROTOCOL.md` describe the older native feasibility probe and still say the repository contains only that probe or that editor development is pending. They are not editor release/install instructions. Publish a current editor-specific handoff, or clearly label these as historical probe procedures.

## Release path supported by the evidence

1. Freeze a reviewed source SHA and verify a fresh editor CI run for that SHA. Download the exact artifact and compare the IPA/source/archive hashes to its manifest; verify ZIP paths and embedded bundle metadata independently.
2. For limited device testing, use the authorized Apple Developer team's matching bundle ID, distribution certificate/private key, registered test device and ad hoc profile, then export and inspect a signed IPA. [Apple's ad hoc profile guidance](https://developer.apple.com/help/account/provisioning-profiles/create-an-ad-hoc-provisioning-profile/) and [registered-device distribution guide](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices) describe the requirements.
3. Install only through that authorized internal channel and record the signed artifact hash, profile/device eligibility, installed version/build and exact target iOS build. The unsigned CI artifact by itself remains a build candidate, not an installable test app.
4. Only after a physical-device pass should release language claim behavior for Photos imports, map GPS edits, mixed batches, MOV/MP4, PNG, Files export, or iCloud Photos. [Apple's iCloud.com instructions](https://support.apple.com/en-ca/guide/icloud/-mmb5dbaf376f/icloud) describe the user-operated web upload; [Apple's iCloud Photos overview](https://support.apple.com/en-us/108782) describes sync and original-format storage, but neither certifies this app's outputs.

Apple's [Enterprise Program description](https://developer.apple.com/programs/enterprise) confines that channel to proprietary internal employee apps. It is not a public Zlarp distribution route.
